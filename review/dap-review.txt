StreamView vs. Stepper

I'm trying to better understand the relationship between these and whether they can be consolidated or otherwise improved.

As I understand it:

STEPPER

Contains:
* a Vec<SourceWindow<'a>>:
  - *borrowed* source
  - position (byte offset of some record)
  - buffered: two VecDeques of records (both directions)
* a filter
* a batch size
* optional max number of records to scan per fill
* running total of bytes read

Intuition:
- there's a merged, filtered stream from a lot of sources
- you're at a particular spot in each source
- you can walk forward or backwards
- limits on how much work is done per step
  => cancellable, shows progress
- requests to the underlying source are cached, but only near your cursor
  => fast incremental navigation
  => bounded memory usage

Good for:
- Scanning through the whole stream (e.g., summary view, search)

STREAMVIEW: much more complicated
* filter
* rendering options (booleans about what to show)
* cursors: front, back
* records: VecDeque<WindowEntry>
  * raw MergeRecord (source, offset, length, event/error, raw string)
  * Vec<String>: rendered lines of the log record
* eof: indicates whether EOF has been reached in either or both directions
* anchor: describes how the view is anchored:
  - `On` (on a specific record: source_id + offset + line number)
  - `Empty`
  - `PinFront` / `PinBack`
  I assume this is used to figure out if the user changes the filter (say) then what should change.  For example, if you're at the first record and change the filter, and new records appear before that one, you probably want to scroll up.  If you're on the second record (`On`), you don't.
* parse_stats
* search_resume: Option<SearchResumePoint>:
  - this is used to keep track of where to resume a search when one "step" didn't find anything
* materialized: ???
  - events: Vec<Row>: one entry per event/error
  - formatted: Vec<String>: one entry per displayed line
  - event_for_line: tells you which event corresponds to line i
  - first_line_for_event[i]: tells you which line is the first one for record i

Intuition:
- this tracks a window of events that can be extended in either direction
- stores a bunch of rendered state that Stepper consumers might not care about

I want to better understand how StreamView works.

There are a few reasons I'm trying to dig into this, which boil down to:

- bugs
- performance
- comprehensibility

Buggy behavior I've seen:

- In the middle of a filtered stream, apply filter, finds no records.  Hit `g` and I see records.
- Bytes scanned can exceed total bytes.
- Records scanned sometimes shows 0 when it's scanning.
- When you hit `G` to scroll to bottom, it's goofy:
  - starts empty
  - starts pushing records in from the top
  - pushes more than it should
  - then scrolls to the end again

Performance:
- Several operations seem to hang with no progress/feedback
  - loading a session with multiple tabs
  - sometimes? re-applying a filter?  I'm not clear on exactly when
  - summary with selective filter (I diagnosed this above)
- Search slows down exponentially
  - looks like it's using a ton of memory, then goes past the end
  - afterwards, it's super sluggish -- 100% on-CPU
    - it was 60% on-CPU just sitting there!
      - this is lots of memcpy in cursor_before_record, doing rendering
  - it's an awful lot of `lumem`free`!

I want to better understand StreamView anyway since I want to take ownership for this.  But I also want to have some intuition for understand these behaviors.  Eventually, I want to make sure every operation that could take a while provides progress and the ability to cancel.

Comprehensibility:
- Both of these cache a contiguous range of records.
- Both support incremental extension in either direction.
- Both support changing the filter without changing where you are, I think
- StreamView:
  - contains more information about position *within* the cached window.  It's two positions, plus how that window is anchored.
  - contains rendered data

Claude admits:

>   So the consequence: Stepper's bidirectional buffer is effectively dead code in this
   caller.  Within a single fetch, only one direction is walked, and the Stepper is
  dropped immediately after.  Stepper here is functioning as a one-shot batch fetcher
   driven from a saved Cursor; the long-lived per-source lookahead/lookbehind it was
  designed around is provided one level up, by StreamView's own window.

Questions:
- What uses step_backward() then?
  - seeit, when given `--before`
  - StreamView, when extending backward
- A lot of the stuff the StreamView is trying to do seems much more complex with its implementation.  e.g., advance_time_forward() would be easy with the Stepper.  But with the StreamView, it's a mess of fiddly logic and accounting
  - I feel like there's an abstraction here where you can advance the anchor like a stepper and then rebuild the window around it?


Ideas around StreamView vs. Stepper:
- Stepper probably needs to not borrow in order to do this
- Could use some naming clarity:
  - regarding the various positions (RecordKey, LogStreamPosition, what else?)
    - merged stream vs. individual source
    - physical position (byte offset) or logical one (timestamp + ordinal?)
    - what about "index into [some window]"?
- It was tempting to try to enhance Stepper to better represent what StreamView needs -- a cached window of records.  However, Stepper doesn't keep a *merged* view, and it keeps a bounded cache per source.  Need to think this through.
- I almost want to rebuild functionality from scratch.  It'd be useful to have a clearer picture of what's used
